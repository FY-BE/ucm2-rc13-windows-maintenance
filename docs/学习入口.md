# Windows ConfigStudio 学习入口

> 基于源码基线 `a704b349a5c8eccad7e82ad0d5b0fffbbaa19799`。本文以 Qt/CMake 工程真实 target 和调用链为入口。

## 一图读懂（文字主线）

从 `source/ucm_windows_config_next_ui/CMakeLists.txt` 进入构建；`main.cpp`/`Main.qml` 是应用入口，`backend/` 承担配置会话、USB 参数、运行时状态和传输，`components/` 与页面 QML 负责界面，`tests/` 保存离线测试与 HIL 入口，`scripts/` 负责打包/辅助构建。

## 首读顺序

1. `CMakeLists.txt`：确认 target、Qt 模块、libusb 和测试开关。
2. `main.cpp`、`Main.qml`：确认 UI 启动和后端注册。
3. `backend/config_session.*`、`config_transport.h`：理解配置会话与传输边界。
4. `backend/usb_*`、`runtime_status_model.*`：理解 USB 和运行态数据流。
5. `tests/`：先读离线测试，再区分 HIL/USB 测试。

## 当前可确认的模块地图

| 模块 | 入口/目录 | 学习问题 |
|---|---|---|
| 构建 | `CMakeLists.txt` | target、Qt、libusb 如何组合？ |
| UI | `main.cpp`, `Main.qml`, `components/` | 页面如何调用后端？ |
| 配置会话 | `backend/config_session.*` | 配置生命周期和失败语义是什么？ |
| USB/运行态 | `backend/usb_*`, `runtime_status_model.*` | 数据如何校验、传输和显示？ |
| 测试 | `tests/` | 哪些是离线，哪些依赖真实设备？ |
| 打包 | `scripts/`, `packaging/` | 如何从源码得到可交付程序？ |

## 当前已知的维护提示

- Windows 头的 `max` 宏会影响 `std::max`；当前构建验证使用过 `/DNOMINMAX`，是否固化为源码/公共编译选项需单独评审。
- CTest、offscreen UI 和 USB/HIL 不是同一层级的证据。
- `build/` 中的程序必须绑定源码 full commit 和构建参数后才能进入交付判断。

## 第一个维护练习

沿 `Main.qml → backend/config_session → config_transport` 追一条配置操作路径，先写出输入、状态变化、失败表现和测试入口，再决定是否修改 C++ 或 QML。
